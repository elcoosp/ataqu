## Security Review: Ataqu Codebase

### Summary
- **Findings**: 6 (2 Critical, 2 High, 1 Medium, 1 Low)
- **Risk Level**: Critical
- **Confidence**: High

The codebase exhibits several severe security flaws, including SQL injection, race conditions in inventory management, and SSRF via workflow webhooks. Additionally, an admin Unix socket lacks authentication, and SSO endpoints are misconfigured. Immediate remediation is required for the critical and high-severity issues.

---

### Findings

#### [VULN-001] SQL Injection in Raw SQL Endpoint (Critical)
- **Location**: `ataqu-api/src/handlers/vista.rs:execute_raw_sql` and `ataqu-infra-repositories/src/vista_repo_impl.rs:execute_raw_sql`
- **Confidence**: High
- **Issue**: The endpoint `/api/vista/raw-sql` accepts a SQL query from the user and executes it directly after only rudimentary validation (checks for `SELECT`/`WITH` and disallows semicolons). Although access is restricted to users with the `admin` role, an attacker who compromises an admin account or finds a privilege escalation vector can run arbitrary read-only SQL queries against the database.
- **Impact**: An attacker with admin privileges can exfiltrate all data from the database, including user credentials, PII, financial records, and internal metadata. The validation can be bypassed using advanced SQL constructs (e.g., `SELECT ...;` is blocked, but `WITH` or subqueries can still perform damaging reads).
- **Evidence**:
  ```rust
  // ataqu-api/src/handlers/vista.rs
  pub async fn execute_raw_sql(
      State(state): State<AppState>,
      auth: AuthContext,
      Json(payload): Json<RawSqlRequest>,
  ) -> ApiResult<Json<Vec<serde_json::Value>>> {
      if !auth.has_role("admin") {
          return Err(ApiResponseError::Forbidden("Admin access required".to_string()));
      }
      let results = state
          .vista_service
          .execute_raw_sql(auth.tenant_id, &payload.sql)
          .await
          ...
  }
  // ataqu-infra-repositories/src/vista_repo_impl.rs
  async fn execute_raw_sql(&self, tenant_id: &TenantId, sql: &str) -> Result<Vec<serde_json::Value>, String> {
      let wrapped_sql = format!("SELECT jsonb_agg(row_to_json(t)) as data FROM ({}) t", sql);
      // No parameterization – user-provided SQL is interpolated.
  }
  ```
- **Fix**:
  - Remove the raw SQL endpoint entirely, or restrict it to a dedicated administrative interface with strong access controls and audit logging.
  - If absolutely necessary, use parameterized queries and a rigorous allowlist of permitted operations (not just prefix checks).

#### [VULN-002] Race Condition in Stock Updates (Critical)
- **Location**: `ataqu-application/src/vault_service.rs:update_stock`
- **Confidence**: High
- **Issue**: The `update_stock` method retrieves a variant, adjusts its stock via `adjust_stock` (which only performs an in-memory check), and then saves it back. There is no atomic database update or locking. Two concurrent requests can read the same stock value, both perform the subtraction, and both write back, potentially allowing stock to drop below zero or oversell beyond available quantity.
- **Impact**: An attacker can cause negative stock (violating business rules) or oversell items, leading to financial loss, customer dissatisfaction, and inventory inconsistencies. This is a classic TOCTOU race condition.
- **Evidence**:
  ```rust
  // ataqu-application/src/vault_service.rs
  pub async fn update_stock(&self, cmd: UpdateStockCommand) -> VaultResult<Variant> {
      let variant = self.get_variant(cmd.tenant_id, cmd.variant_id).await?;
      let new_variant = variant.adjust_stock(cmd.delta, self.clock.as_ref())?;  // <-- in-memory check
      self.repo.save_variant(&new_variant).await?;  // <-- no atomicity
      ...
  }
  ```
  An atomic update helper exists in `ataqu-infra-repositories/src/vault_repo.rs` (`decrement_stock`) but is never used.
- **Fix**:
  - Use atomic database updates with conditional checks, e.g.,
    ```sql
    UPDATE vault.variants
    SET stock_quantity = stock_quantity + $1
    WHERE id = $2 AND stock_quantity + $1 >= 0
    RETURNING *;
    ```
  - Alternatively, use row-level locking (`SELECT ... FOR UPDATE`) within a transaction.
  - Implement optimistic concurrency control (version field) for stock as well.

#### [VULN-003] SSRF via Workflow Webhook Actions (High)
- **Location**: `ataqu-application/src/spark_service.rs:ActionDispatcher::dispatch` and `ataqu-domain-spark/src/action.rs:Webhook`
- **Confidence**: High
- **Issue**: SPARK workflows can include a `Webhook` action that performs an HTTP request to a user‑supplied URL. When a workflow is triggered, the action dispatcher sends an HTTP request to the configured URL without any validation. An attacker who can create or modify workflows (endpoints `/api/spark/workflows` are authenticated but not restricted to admins) can set the webhook URL to an internal service (e.g., `http://169.254.169.254/latest/meta-data/` or internal network endpoints) and cause SSRF.
- **Impact**: SSRF can be used to access cloud metadata endpoints (IAM credentials), internal services, and network scanners, potentially leading to data exfiltration or lateral movement.
- **Evidence**:
  ```rust
  // ataqu-application/src/spark_service.rs (ActionDispatcher implementation)
  Action::Webhook { url, method, body, headers } => {
      let client = reqwest::Client::new();
      let mut req = match method.to_uppercase().as_str() {
          "POST" => client.post(url),
          ...
      };
      req = req.json(&body);
      req.send().await.map_err(|e| e.to_string())?;
  }
  // No allowlist or restrictions on the URL.
  ```
- **Fix**:
  - Implement an allowlist of permitted domains for webhook actions.
  - Block internal IP ranges (RFC 1918, loopback, link-local, metadata IPs).
  - Disable redirects and validate the resolved IP before making the request.
  - Restrict workflow creation/modification to trusted roles (e.g., admins only).

#### [VULN-004] Admin Unix Socket Lacks Authentication (High)
- **Location**: `ataqu-admin/src/main.rs`
- **Confidence**: High
- **Issue**: The admin server binds to `/tmp/ataqu-admin.sock` and accepts any incoming connection. It currently only logs received commands, but the code contains a `TODO` to authenticate and execute commands. If this socket is ever used to execute commands, any local user who can connect to the socket (default permissions are world-writable) could send arbitrary admin commands. Even without execution, the lack of authentication is a critical design flaw.
- **Impact**: A local attacker could eventually execute arbitrary administrative commands, leading to full system compromise. Currently it's only a logging vulnerability (information disclosure via logs), but the design is unsafe.
- **Evidence**:
  ```rust
  // ataqu-admin/src/main.rs
  let listener = UnixListener::bind(socket_path)?;
  ...
  match listener.accept().await {
      Ok((mut stream, _)) => {
          tokio::spawn(async move {
              let mut buffer = [0; 1024];
              match stream.read(&mut buffer).await {
                  Ok(bytes_read) => {
                      let command = String::from_utf8_lossy(&buffer[..bytes_read]);
                      tracing::info!("Received admin command: {}", command);
                      // TODO: Parse command, authenticate, write to audit_logs, and execute.
                      let response = format!("Command '{}' received and logged.\n", command);
                      ...
                  }
                  ...
              }
          });
      }
  }
  ```
- **Fix**:
  - Remove the admin socket or restrict its permissions (e.g., `chmod 600` and only allow the `admin` user to access it).
  - Implement strong authentication (e.g., mutual TLS or a shared secret).
  - Ensure that all operations are audited and logged.
  - If not used, remove the code entirely.

#### [VULN-005] SSO Login Endpoints Behind Authentication (Medium)
- **Location**: `ataqu-api/src/handlers/aegis.rs:sso_login`, `sso_callback` and `ataqu-api/src/lib.rs` route mounting
- **Confidence**: High
- **Issue**: The SSO login and callback endpoints are intended to be public, but they are mounted under the `private_routes` group, which applies the authentication middleware. This makes them require a valid JWT to access, breaking the SSO flow and preventing users from logging in via SSO.
- **Impact**: SSO functionality is broken, leading to a denial-of-service for SSO users. Not a direct security vulnerability, but a severe misconfiguration that should be fixed.
- **Evidence**:
  ```rust
  // ataqu-api/src/lib.rs
  let private_routes = Router::new()
      .nest("/api/aegis", aegis_routes())  // includes /sso/login, /sso/callback
      .layer(axum::middleware::from_fn_with_state(state.clone(), auth_middleware));
  ```
- **Fix**:
  - Move the SSO endpoints to a separate public router (e.g., `public_routes`) that does not require authentication.
  - Ensure that the callbacks correctly handle the OAuth2 state and exchange.

#### [VULN-006] Use of SHA256 for API Key Hashing (Low)
- **Location**: `ataqu-domain-aegis/src/api_key.rs:generate_api_key`
- **Confidence**: High
- **Issue**: API keys are hashed using SHA256 before storage. While SHA256 is not broken, it is a fast hash and susceptible to brute-force attacks if the keys are not sufficiently random and high-entropy. For credential storage, Argon2 or bcrypt are recommended.
- **Impact**: In the unlikely event that the hashed API keys are exposed (e.g., via SQL injection), an attacker could crack weak keys much faster than with a slow hashing algorithm.
- **Evidence**:
  ```rust
  use sha2::{Digest, Sha256};
  let mut hasher = Sha256::new();
  hasher.update(raw_key.as_bytes());
  let key_hash = format!("{:x}", hasher.finalize());
  ```
- **Fix**:
  - Use a key-derivation function (KDF) such as Argon2id or bcrypt for hashing API keys.
  - Ensure that keys are generated with sufficient entropy (e.g., 128 bits or more).

### Needs Verification

#### [VERIFY-001] Potential Lack of Input Validation on Tenant ID in Public Endpoints
- **Location**: Public endpoints like `/api/sond/forms/:id/submit`, `/api/tempo/public/:tenant_id/...`, `/api/spark/webhooks/:tenant_id/:workflow_id`
- **Question**: These endpoints accept a `tenant_id` as a path parameter. They do not appear to validate that the caller has access to that tenant. For public endpoints (e.g., form submissions), this may be acceptable, but for webhook triggers, an attacker could guess tenant IDs and attempt to trigger workflows. Confirm that these endpoints are properly scoped (e.g., webhook secret is required for SPARK webhooks, and SOND submissions are public by design).

---

### Recommendations Summary
1. **Immediate**: Remove or secure the raw SQL endpoint. Use parameterized queries and restrict to super-admins with separate audit logs.
2. **Immediate**: Implement atomic stock updates in the vault service using conditional `UPDATE` statements or row locking.
3. **High**: Add URL validation and IP filtering for webhook actions in SPARK workflows.
4. **High**: Either remove the admin Unix socket or add proper authentication and restrict permissions.
5. **Medium**: Move SSO endpoints to public routes.
6. **Low**: Upgrade API key hashing to Argon2id.

### Overall Assessment
The codebase shows a strong separation of concerns with domain-driven design, but critical security oversights exist in areas involving raw user‑controlled input (SQL, URLs) and concurrency (stock updates). Immediate patching of the critical and high findings is strongly advised.
