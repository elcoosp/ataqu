**3,100 lines of domain logic. 2,100 lines of API handlers. 10 apps.**

---

We sat down to write the business logic and the API layer for 10 SaaS applications.

CRM, chat, HR, inventory, analytics, automation, scheduling, forms, docs, security. Ten complete business domains.

We expected this to take days. It took an afternoon.

The hardest part was not writing the code itself. It was not writing the code that everyone else usually writes.

---

### The usual 80%

In 2026, Rust is the default choice for serious backends. Axum handles HTTP. SeaORM handles the database. Tokio handles async. Tracing handles observability.

The ecosystem has solved the hard problems.

About 80% of a SaaS backend is boilerplate: auth, CRUD, database migrations, background jobs, multi-tenancy, PII redaction.

We did not write that 80%.

We wrote the 20% that makes our apps unique. The business logic. The rules that make CINQ a CRM and not just a database. The validations that prevent bad data. The events that tell the rest of the system what happened.

And we wrote the API handlers that expose that logic over HTTP, with idempotency, PII serialization, and error mapping baked in.

The integration layer handles the rest.

---

### The Domain Layer – Pure Functions

The domain layer is pure Rust functions. No I/O, no HTTP, no database connections. It never reads the system clock or generates random numbers.

Creating a user in AEGIS:

```rust
pub fn create_user(
    cmd: CreateUserCommand,
    id_gen: &impl IdGenerator,
    clock: &impl Clock,
) -> UserCreated {
    let user_id = id_gen.new_uuid_v7();
    let now = clock.now();
    UserCreated { user_id, email: cmd.email, created_at: now }
}
```

No SQL, no network, no async. Just a command, an ID, a timestamp, and an event.

The `IdGenerator` and `Clock` traits come from a shared kernel. In production they produce UUIDv7 and `SystemTime`. In tests we inject mocks.

The domain layer never calls `Uuid::now_v7()` or `SystemTime::now()`. It doesn't know what time it is. It only knows that someone will tell it.

This makes every domain function testable without a database, deterministic, and portable.

### Ten Domains, One Pattern

We wrote domain crates for 10 apps. Each defines entities, commands, events, repository traits, validation logic, and error types.

The repository traits are the key. They describe what the domain needs without specifying how. For example, the CINQ contact repository:

```rust
pub trait ContactRepository: Send + Sync {
    fn save_contact(&self, contact: &Contact) -> impl Future<Output = CinqRepositoryResult<()>> + Send;
    fn find_contact_by_id(&self, tenant_id: &TenantId, id: Uuid) -> impl Future<Output = CinqRepositoryResult<Option<Contact>>> + Send;
    fn list_contacts(&self, tenant_id: &TenantId, limit: u64, offset: u64) -> impl Future<Output = CinqRepositoryResult<Vec<Contact>>> + Send;
}
```

The infrastructure layer implements these using SeaORM and raw SQL. The domain layer does not care how data is stored. It only knows what operations are available.

This keeps business logic isolated from database migrations, connection pools, and transaction management. Change the database? The domain does not care. Swap SeaORM for something else? The domain does not care.

### Validation – Pure, Not Hacked

Every domain includes validation logic.

In CINQ, deal amounts must be positive, pipeline stage orders non-negative, contact names non-empty.

In SOND, question options must be valid, rating ranges between 1 and 10, conditional visibility parseable.

In DIAL, message lengths have a maximum, channel names have limits, direct messages require exactly two participants.

These are pure functions returning `Result` with domain errors. They run before any event is produced. By the time data reaches the repository, it is already valid.

### The API Layer – Handlers with Idempotency and PII Safety

The API layer is built with Axum and sits on top of the application services.

Each handler extracts the `Idempotency-Key` header for mutating endpoints. It uses `ApiEmail` wrapper structs to serialize PII. The newtypes themselves do not implement `Serialize`, so PII never leaks into logs (ADR-007). It maps domain and service errors to proper HTTP status codes: 422, 404, 409, 503 with `Retry-After`.

For example, the AEGIS login handler:

```rust
pub async fn login<R, O, D>(
    State(state): State<AegisHandlerState<R, O, D>>,
    IdempotencyKeyHeader(idempotency_key): IdempotencyKeyHeader,
    AxumJson(req): AxumJson<LoginRequest>,
) -> Response { ... }
```

It uses the same generic constraints as the service, ensuring type safety from the wire to the database.

We have handlers for all 10 apps: AEGIS (auth), CINQ (CRM), DIAL (chat), PAUSE (HR), PIVOT (docs), SOND (forms), SPARK (automation), TEMPO (scheduling), VAULT (inventory), and VISTA (analytics).

Each module is lean. The service layer does the heavy lifting; the handlers focus on HTTP semantics, idempotency, and error presentation.

### What We Did Not Write

We did not write database migrations, connection pools, the outbox dispatcher, idempotency guards, tenant isolation via RLS, or PII redaction infrastructure.

All of that was built yesterday as the integration layer (1,920 lines of Rust).

The domain crates are dependency light: `serde` for serialization, `chrono` for time, `uuid` for identifiers, `thiserror` for errors, `ataqu-kernel` for shared traits. No async runtime, no database driver, no web framework. Just Rust.
