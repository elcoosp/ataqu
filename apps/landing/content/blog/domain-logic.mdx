I sat down a few hours ago to write the domain logic for 10 SaaS applications. CRM. Chat. HR. Inventory. Analytics. Automation. Scheduling. Forms. Docs. Security. Ten complete business domains.

I expected this to take days. It took an afternoon. The hardest part wasn't writing the code. It was not writing all the other code that everyone else usually writes.

In 2026, Rust has gone from an interesting language to the default choice for new serious backends. Microsoft is rewriting Windows in Rust. The ecosystem has tools for everything: Axum for HTTP, SeaORM for databases, Tokio for async, tracing for observability. The patterns are documented. The boilerplate can be generated.

About 80% of what you'd normally write for a SaaS backend is boilerplate. Auth. CRUD. Database migrations. Background jobs. Multi-tenancy. The industry has solved these problems.

We decided not to write that 80%. We wrote the 20% that makes our apps unique and let the architecture handle the rest.

The 20% we wrote today is the domain layer. Pure Rust functions that encode business rules. No I/O. No HTTP. No database connections. No system clock reads. No random number generation.

For example, creating a user in AEGIS:

```rust
pub fn create_user(
    cmd: CreateUserCommand,
    id_gen: &impl IdGenerator,
    clock: &impl Clock,
) -> UserCreated {
    let user_id = id_gen.new_uuid_v7();
    let now = clock.now();
    UserCreated { user_id, email: cmd.email, created_at: now }
}
```

That's it. No SQL. No network calls. No async. Just a function that takes a command, generates an ID and a timestamp via injected traits, and returns an event.

The `IdGenerator` and `Clock` traits come from a shared kernel crate. In production, they produce UUIDv7 and `SystemTime`. In tests, we inject mocks that return deterministic values. The domain layer never calls `Uuid::now_v7()` or `SystemTime::now()` directly. It doesn't know what time it is. It only knows that someone will tell it.

This makes every domain function testable without a database, deterministic, and portable.

We wrote domain crates for 10 apps. Each one defines entities, commands, events, repository traits, validation logic, and error types.

The repository traits are interesting. They describe what the domain needs from persistence without specifying how. For example, the CINQ contact repository:

```rust
pub trait ContactRepository: Send + Sync {
    fn save_contact(&self, contact: &Contact) -> impl Future<Output = CinqRepositoryResult<()>> + Send;
    fn find_contact_by_id(&self, tenant_id: &TenantId, id: Uuid) -> impl Future<Output = CinqRepositoryResult<Option<Contact>>> + Send;
    fn list_contacts(&self, tenant_id: &TenantId, limit: u64, offset: u64) -> impl Future<Output = CinqRepositoryResult<Vec<Contact>>> + Send;
}
```

The infrastructure layer implements these using SeaORM and raw SQL. The domain layer doesn't care how data is stored. It only knows what operations are available. This keeps business logic isolated from database migrations, connection pools, and transaction management.

Every domain includes validation logic that prevents bad data from reaching the database.

- In CINQ, we validate that deal amounts are positive, pipeline stage orders are non-negative, and contact names aren't empty.
- In SOND, we validate form question options, rating ranges, and conditional visibility logic.
- In DIAL, we enforce maximum message lengths, channel name limits, and the rule that direct messages require exactly two participants.

These validations are pure functions that return `Result` with domain errors. They run before any event is produced. By the time data reaches the repository layer, it's already valid.

We didn't write HTTP handlers, database migrations, connection pools, the outbox dispatcher, idempotency guards, tenant isolation, or PII redaction. All of that infrastructure was built last week. Today, we just wired the business logic into it.

The domain crates are dependency-light. They pull in `serde` for serialization, `chrono` for time, `uuid` for identifiers, `thiserror` for errors, and `ataqu-kernel` for shared traits. No async runtime. No database driver. No web framework. Just Rust.

This means the domain crates compile fast, test fast, and are easy to reason about. They're also easy to replace. If we ever changed the database or the web framework, the domain logic wouldn't need to change.

In 2020, building 10 SaaS apps in a single afternoon would have been impossible. The frameworks weren't there. The patterns weren't documented. You'd have spent weeks just figuring out how to structure the code.

In 2026, the hard problems have been solved. We wrote the business logic. And because the infrastructure was already in place, it took an afternoon.

Tomorrow, we build the application layer. The services that orchestrate the idempotency flow, call the domain functions, persist events, and append to the outbox. Then the API handlers. Then the frontend SPAs.

The business logic is written, tested, and ready.
