### The Domain Layer – Pure Functions

The domain layer is **pure Rust functions** that encode business rules.

No I/O. No HTTP. No database connections. No system clock reads. No random number generation.

Creating a user in AEGIS:

```rust
pub fn create_user(
    cmd: CreateUserCommand,
    id_gen: &impl IdGenerator,
    clock: &impl Clock,
) -> UserCreated {
    let user_id = id_gen.new_uuid_v7();
    let now = clock.now();
    UserCreated { user_id, email: cmd.email, created_at: now }
}
```

No SQL. No network calls. No async.

Just a function that takes a command, generates an ID and a timestamp via injected traits, and returns an event.

**The `IdGenerator` and `Clock` traits** come from a shared kernel. In production, they produce UUIDv7 and `SystemTime`. In tests, we inject mocks that return deterministic values.

The domain layer never calls `Uuid::now_v7()`. It never calls `SystemTime::now()`.

It doesn't know what time it is. It only knows that someone will tell it.

**This makes every domain function testable without a database. Deterministic. Portable.**

### Ten Domains, One Pattern

We wrote domain crates for **10 apps**. Each one defines:

- Entities (e.g., `Contact`, `Deal`, `Message`)
- Commands (e.g., `CreateContactCommand`)
- Events (e.g., `ContactCreated`, `DealWon`)
- Repository traits (what the domain needs from persistence – without specifying how)
- Validation logic
- Error types

**The repository traits are the key.**

They describe what the domain needs without specifying how. For example, the CINQ contact repository:

```rust
pub trait ContactRepository: Send + Sync {
    fn save_contact(&self, contact: &Contact) -> impl Future<Output = CinqRepositoryResult<()>> + Send;
    fn find_contact_by_id(&self, tenant_id: &TenantId, id: Uuid) -> impl Future<Output = CinqRepositoryResult<Option<Contact>>> + Send;
    fn list_contacts(&self, tenant_id: &TenantId, limit: u64, offset: u64) -> impl Future<Output = CinqRepositoryResult<Vec<Contact>>> + Send;
}
```

The infrastructure layer implements these using SeaORM and raw SQL. The domain layer doesn't care how data is stored.

**It only knows what operations are available.**

This keeps business logic isolated from database migrations, connection pools, and transaction management. Change the database? The domain doesn't care. Swap SeaORM for something else? The domain doesn't care.

### Validation – Pure, Not Hacked

Every domain includes validation logic that prevents bad data from reaching the database.

**In CINQ:**
- Deal amounts must be positive.
- Pipeline stage orders must be non-negative.
- Contact names can't be empty.

**In SOND:**
- Form question options must be valid.
- Rating ranges must be between 1 and 10.
- Conditional visibility logic must be parseable.

**In DIAL:**
- Message lengths have a maximum.
- Channel names have limits.
- Direct messages require exactly two participants.

These validations are **pure functions** that return `Result` with domain errors. They run before any event is produced.

By the time data reaches the repository layer, it's already valid.

### The API Layer – Handlers with Idempotency and PII Safety

The API layer is built with **Axum** and sits on top of the application services.

Each handler:

- Extracts the `Idempotency-Key` header (UUIDv4) for mutating endpoints.
- Uses `ApiEmail` wrapper structs to serialize PII — the newtypes themselves do **not** implement `Serialize`, so PII never leaks into logs (ADR-007).
- Maps domain and service errors to proper HTTP status codes (422, 404, 409, 503 with `Retry-After`).

For example, the AEGIS login handler:

```rust
pub async fn login<R, O, D>(
    State(state): State<AegisHandlerState<R, O, D>>,
    IdempotencyKeyHeader(idempotency_key): IdempotencyKeyHeader,
    AxumJson(req): AxumJson<LoginRequest>,
) -> Response { ... }
```

It uses the same generic constraints as the service, ensuring type safety from the wire to the database.

**We have handlers for all 10 apps:** AEGIS (auth), CINQ (CRM), DIAL (chat), PAUSE (HR), PIVOT (docs), SOND (forms), SPARK (automation), TEMPO (scheduling), VAULT (inventory), and VISTA (analytics).

Each handler module is lean — the service layer does the heavy lifting, and the handlers focus on HTTP semantics, idempotency, and error presentation.

### What We Didn't Write

We didn't write database migrations. Connection pools. The outbox dispatcher. Idempotency guards. Tenant isolation via RLS. PII redaction infrastructure.

All of that was built **yesterday** — the integration layer (1,920 lines of Rust).

Today, we just wired the business logic and the API endpoints into it.

**The domain crates are dependency-light:**
- `serde` for serialization.
- `chrono` for time.
- `uuid` for identifiers.
- `thiserror` for errors.
- `ataqu-kernel` for shared traits.

No async runtime. No database driver. No web framework. Just Rust.

This means the domain crates compile fast, test fast, and are easy to reason about.
